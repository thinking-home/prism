## 6. Структурирование библиотеки — СПЕКА СОГЛАСОВАНА (2026-08-11), в работе

Развитие `Prism.Plugins.Library`; ядро (скан/стриминг) не трогаем.

**Модель — две порции данных:**
- *скан* — эфемерный слепок диска (path → fingerprint); отпечатки кэшируются в БД
  по `(path, size, mtime)`, чтобы не пересчитывать после рестарта;
- *библиотека* — персистентная: дерево групп + мета + членство. Путей не знает,
  ключ файла — **fingerprint** (структура переживает переезды/переименования).
  Копии одного контента в разных папках разделяют мету — это осознанно.

**Таблицы:** `Prism_Node(Id, ParentId, Name)` — группы, вложенность через ParentId;
`Prism_NodeItem(NodeId, FileKey)` — членство (файл может быть в нескольких группах);
`Prism_Meta(EntityType, EntityKey, Key, Value)` — свободные ключи и для файлов, и
для групп. Сервер семантики меты НЕ знает (никаких movie/episode; `title` хранится
готовой строкой, склейку делает заполняющий). Старая таблица `Prism_MediaMetadata`
мигрируется в key-value; `PUT /api/media/{id}/metadata` заменяется на общий
`PUT …/meta` (слияние ключей, null — удалить).

**API:** `/api/media` как сейчас (мета подмешивается); `GET /api/library/tree` —
все группы + членство одним запросом (библиотека домашняя — без пагинации, дерево
строит клиент); CRUD групп (перенос ветки = смена ParentId); членство
PUT/DELETE. **Поиск — только на клиенте** (фильтрация полного списка в памяти).

**Неконсистентность — штатное состояние, не ошибка:**
- файл на диске без записей — «новый»: виден в корне, мета пустая;
- записи без файла — «осиротевшие»: автоматически НЕ удаляем (диск мог быть
  отключён), в API помечаются `present:false`; чистка — явной командой (GC).

**Правила автозаполнения** — атомарные, декларативные, применяются только к файлам
**без единой записи** в библиотеке. Пометок «обработано» нет намеренно: любая
запись у файла (мета или членство, от правила или от руки) — признак, что его уже
трогали, и правила его больше не касаются; ручные правки не перетираются, а
удаление всех записей файла = «разложить заново по правилам». Для отладки правил
есть режим замены (`POST /api/library/scan?replace=true`): очищает библиотеку
целиком — группы, членство и мету, включая записи файлов, которых нет на диске, —
и раскладывает заново. Включается **только с ручки**, по таймеру замены не бывает:
- правило = **шаблон пути с плейсхолдерами** (упрощённый синтаксис вместо regex),
  напр. вход `*/{series}.s{season}e{episode}*` + действия: путь к узлу дерева
  `Сериалы/{series}` и/или мета-ключи из плейсхолдеров (`season={season}`);
  отображаемое имя — это просто мета-ключ `title`. `{имя}` — непустой кусок
  сегмента пути, `{имя:#}` — только цифры, `*` — любой, в том числе пустой, без
  захвата (нужна для мусора в реальных именах, проверено на живой библиотеке:
  покрытие 189 → 213 из 245). Плейсхолдер прямо перед `*` берёт подряд идущие
  буквы и цифры — иначе две ленивые группы делят строку по минимуму и
  `{episode}*` даёт «0» вместо «01» (поймано на стенде, исправлено). Тип `:#`
  добавлен по итогам прогона на реальной библиотеке: без него `s{season}e{...}`
  цеплялся за буквы в словах и записал «Vechnoe.Siyanie.Chistogo» в сериалы;
- применяются все подходящие по порядку; при совпадении мета-ключа выигрывает
  первое; хранение — секция `Library:Rules` в appsettings (UI/API позже);
- всё умное (TMDB и т.п.) — снаружи через API.

**Недокачанные/изменившиеся файлы — примитивный ремап при скане:**
fingerprint F осиротел → взять его последний путь P из кэша → если в P лежит
файл с fingerprint G≠F и у G нет своих записей — перенести записи F→G (мета,
членство, пометка «обработан»), залогировать; при конфликте (у G есть записи)
не трогать. Пока файл докачивается, записи просто переезжают по цепочке на
актуальный отпечаток при каждом скане — карантинов и таймеров нет намеренно.
Сознательный риск: замена контента по тому же пути наследует мету (правится
руками).

## 7. Клиент библиотеки — «контроллер» (дерево + поиск) — СЛЕДУЮЩИЙ
Отдельное приложение с ролью **«контроллер»** в архитектуре Prism (хост — источник,
плеер — рендерер): просмотр библиотеки и выбор, что смотреть. Серверная часть
готова (п.6: `GET /api/library/tree`, мета в `/api/media`).

- файлы отображаются в виде **дерева**; файл — это листовой узел дерева
  (группирующие узлы — папки/категории из виртуального дерева п.6);
- над деревом — **строка поиска**, фильтрующая дерево: фильтр применяется и к
  файлам, и к группирующим узлам (поиск — только на клиенте, по спеке п.6);
- если узел (группирующий или файл) соответствует фильтру, все его **родительские
  узлы раскрываются**, чтобы совпадение было видно.

План в два шага:
1. **сначала доработать веб-клиент** (Prism.Client) — обкатать дерево с поиском и
   убедиться, что такой интерфейс удобен;
   - ~~просмотр дерева~~ — СДЕЛАНО (2026-08-12): вместо плоской сетки карточек
     `Library.tsx` строит дерево из `/api/library/tree` + `/api/media`. Группы
     свёрнуты (`<details>`, своего состояния не держим) и показывают число файлов
     в поддереве; файлы — ссылки на плеер; отдельно «Вне групп» и записи «нет на
     диске» (`present:false`); шапка со сводкой «файлов / в группах / вне групп».
     Плагин опционален: если `/api/library/tree` недоступна, дерево пустое и все
     файлы показываются плоским списком;
   - **строка поиска** — следующий шаг;
   - замечено на реальной библиотеке: первый заход ждёт `/api/media` ~1 мин
     (ffprobe 248 файлов на холодную), дальше мгновенно. Если станет мешать —
     отдельная задача (дерево можно рисовать, не дожидаясь метаданных);

## 12. Баг: mp4 никогда не попадал в режим `direct` — ИСПРАВЛЕНО (2026-08-12)
`MediaInfo.IsBrowserNative` сравнивал `format_name` от ffprobe со списком имён
целиком, а ffprobe отдаёт **список демуксера** одной строкой:
`"mov,mp4,m4a,3gp,3g2,mj2"` — совпадения не было никогда, и любой mp4 (даже
h264+aac) шёл через HLS-транскодирование вместо дешёвой прямой раздачи с Range.
Теперь строка разбирается по запятым; семейство `matroska` по-прежнему считается
требующим ремукса (настоящий WebM от MKV дёшево не отличить), поэтому `.webm`
тоже идёт через HLS — если понадобится, можно различать по расширению.
Проверено: h264+aac mp4 → `direct` и `206 Partial Content`, mkv и mp4 со старыми
кодеками → `hls`.

## 13. Файлы дорожек: префиксное совпадение даёт ложные привязки
Компаньон ищется по началу имени видео, поэтому к `Фильм.mkv` прицепится
`Фильм 2.srt` — субтитры **другого** фильма, да ещё с подписью «2». Встречается
редко (нужны файлы, чьи имена — префиксы друг друга), но логика некорректная.
Предлагаемое решение: привязывать компаньона к видео с **самым длинным**
совпавшим именем — тогда при наличии `Фильм 2.mkv` его субтитры уйдут к нему, а
не к `Фильм.mkv`. Полностью проблему это не снимает (если `Фильм 2.mkv` в
библиотеке нет, файл всё равно прицепится к `Фильм.mkv`), но убирает основной
сценарий.

## 14. Библиотека — отдельный сервис (агрегация хостов) — СПЕКА СОГЛАСОВАНА (2026-08-17), в работе

Мотивация: хостов с фильмами в сети может быть несколько (например, сетевые
диски, на каждом установлен хост). Библиотека выносится из плагина хоста в
отдельный сервис: собирает файлы со всех хостов в одно дерево, знает плееры в
сети и умеет включать любой фильм на любом плеере. Клиенты (веб, Android)
работают только с библиотекой.

**Роли:** хост = скан + стриминг (плагин библиотеки из хоста удаляется — режим
один, сервис; плагинная инфраструктура остаётся); библиотека = дерево/мета/
правила + агрегация хостов + список плееров + веб-клиент; плеер не меняется
(он и так host-agnostic); лаунчер не меняется (работает со своим локальным
хостом через `/api/resolve` — библиотека ему не нужна).

**Решения:**
- хосты перечисляются в конфиге библиотеки (имя + базовый URL); discovery по
  MQTT — потом, при желании;
- id контентный, поэтому БД библиотеки переезжает без изменений схемы (ключ
  миграций `prism.library` сохраняется, существующая SQLite подхватывается);
  копия фильма на двух хостах — одна запись (дедуп между хостами бесплатно;
  при запуске можно выбрать живой хост); перенос файла **между хостами**
  ремапа не требует — id тот же, запись не осиротеет;
- «файла нет на диске» и «хост недоступен» — **одно состояние** `present:false`;
  записи не трогаются (философия «неконсистентность — штатное состояние»
  масштабируется на хосты); ремап при недоступном хосте не запускается
  (преемника спрашивать не у кого — пропуск, без случайных переездов записей);
  `gc` при выключенном хосте опасен так же, как сейчас при отключённом диске;
- каталог клиентам отдаёт библиотека: слияние хостов + подмешанная мета,
  `streamUrl` абсолютные (указывают на хост-владельца; браузер стримит с хоста
  напрямую, CORS уже открыт); библиотека помнит, какой хост последним видел
  каждый id (бухгалтерия для present/ремапа);
- плееры: библиотека подписывается на `prism/player/+/info|state` и даёт
  `GET /api/players` + `POST /api/players/{id}/open` (MQTT-публикацию делает
  сама) — клиенты про MQTT не знают; ThinkingHome (п.8) — тонкий клиент этого
  же API;
- веб-клиент раздаёт библиотека; дефолт «URL сервера» = same-origin (настройка
  остаётся для dev); Android-контроллер из п.7 становится шагом этого пункта;
- структура зеркалит хост: `Prism.Library` (ядро) + `.Console` + `.Service` +
  `.Setup`; **проекты `*.Console` считаем вариантом для unix-систем, а не
  dev-запуском** — конфиг у них боевой (относится и к `Prism.Host.Console`);
- отдельный инсталлятор; в MSI библиотеки едет npm-сборка веб-клиента (сборке
  инсталлятора нужен Node);
- на будущее (сейчас не проектируем): «умный» поиск (мини-нейросеть, серверный
  `/api/search` поверх меты и названий) — вынос в сервис делает его возможным
  (плагин одного хоста не видел бы весь каталог), модель данных менять не надо.

## 15. Клиент тянул все дорожки субтитров сразу — ИСПРАВЛЕНО (2026-08-28)

Симптом: хост «подвисал» — не отдавал видео в веб-клиенте и не сразу
останавливался. Разбор по логам: приложение было живо (библиотека получала от
него ответы за 4–8 мс, фоновый цикл тикал по расписанию, ни одного WRN/ERR),
вставало именно воспроизведение. Открывали «Облачный атлас» — 25.8 ГБ,
**5 аудиодорожек и 6 текстовых субтитров**, медиатека лежит на внешнем
USB-HDD.

Причина: `VideoPlayer` рендерил `<track>` на каждую текстовую дорожку, браузер
запрашивал их все сразу при открытии страницы, а каждый такой запрос на хосте —
отдельный проход ffmpeg по всему контейнеру (`SubtitleService`, отмену запроса
он игнорирует намеренно: результат общий и кэшируемый). Итого шесть полных
чтений 25-гигабайтного файла параллельно с сессиями видео и аудио того же файла:
на USB-диске (замер — ~55 МБ/с в один поток, полный проход ≈ 8 минут) это
надолго обрушивает скорость, сегменты перестают успевать. Ожидание сегмента —
60 с на попытку, до трёх попыток, поэтому запрос висит до ~3 минут молча.
Перезагрузка страницы добавляла новые сессии видео/аудио (LRU держит до трёх на
файл). Медленная остановка — следствие: сессии гасятся по очереди с ожиданием
до 3 с каждая плюс чистка временных папок.

Исправление (клиент): в DOM живёт только выбранная дорожка — при «Выкл» не
грузится ни одна, при переключении ровно одна новая. Проверено на ролике с
тремя дорожками: при открытии ноль запросов `subtitle/*.vtt` (было три),
после выбора дорожки — ровно один, после переключения — ещё один; реплики
показываются.

Не сделано, кандидаты на будущее (решать отдельно):
- хост молчит про воспроизведение: старт сессий, вывод ffmpeg и вытеснение
  пишутся в `LogDebug` при уровне `Information`, запросы ASP.NET — на `Warning`.
  Стоит вынести старт/остановку сессий на `Information` и предупреждать, когда
  ожидание сегмента превысило N секунд;
- извлечения субтитров ничем не ограничены по параллельности и не отменяются;
- медиатека на USB-HDD — узкое место сама по себе.

## 16. Веб-клиент на Mantine — СДЕЛАНО (2026-08-28)

Своей вёрстки и своих стилей в клиенте больше нет: `styles.css` (363 строки)
удалён, интерфейс собран из компонентов Mantine 9.5 (`@mantine/core` +
`@mantine/hooks`), тёмная схема по умолчанию через `MantineProvider`. Каркас —
`AppShell` с шапкой; настройка адреса библиотеки переехала в `Modal`; дерево

— `Box component="video"`; дебаг-панель — `SimpleGrid` из `Paper`-плиток и `Card`
на сессию с `Progress` вместо самодельных полосок. Из сырых элементов остались
только `<form>` в диалоге настроек и `<track>` в плеере — соответствий им в
Mantine нет.

Самодельный SVG-график CPU из дебаг-панели убран: это была ровно та кастомная
вёрстка, от которой уходили, а `Sparkline` живёт в `@mantine/charts` и тянет
recharts. Вернуть график — отдельное решение.

Проверено вживую на 247 файлах: список с бейджами и подписями, страница фильма

группой. Раскрытие групп и анимацию модалки во встроенном браузере проверить
нельзя — там не работает `requestAnimationFrame` (см. HANDOFF).
