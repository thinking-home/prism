# Сборка полного релиза

`release.py` собирает релиз из чистого рабочего дерева и после успешной сборки
создаёт локальный Git-тег `v<version>` на исходном коммите. Перед запуском
закоммитьте изменения, включая новые файлы, либо уберите их в stash.
Это сборочный скрипт: он не устанавливает приложения, не меняет службы
и не отправляет APK на устройства.

## Требования к машине сборки

- Windows x64: WiX собирает и проверяет MSI на Windows. Linux-пакеты публикуются
  с целевой платформой `linux-x64`, WSL для сборки не нужен.
- Python 3.12+ без дополнительных пакетов.
- Git с доступным коммитом HEAD.
- .NET SDK 10, Node.js/npm из требований `Prism.Client` (используется `npm ci`).
- JDK 25, например JBR из Android Studio. Старую Java устанавливать не требуется.
- Android SDK: Platform 36 и Build Tools 36.0.0; лицензии SDK должны быть приняты.
- `keystore.properties` в обоих Android-проектах со ссылкой на существующий ключ.
  Пароли передавать скрипту не нужно. Без ключей релиз завершится ошибкой.
- Доступ к NuGet, npm, Google Maven, Gradle, gyan.dev и GitHub при первом запуске.

## Запуск

Из корня репозитория в PowerShell:

```powershell
python scripts/release.py --version 0.4.0 --android-version-code 2 --java-home "C:/Program Files/Android/Android Studio/jbr"
```

Путь Java можно задать через `JAVA_HOME`, путь SDK — через `--android-sdk`,
`ANDROID_HOME` или `ANDROID_SDK_ROOT`. По умолчанию SDK ищется в
`%USERPROFILE%/AppData/Local/Android/Sdk`.

`--check` проверяет чистоту Git, отсутствие тега, наличие локальных инструментов и
файлов подписи без сборки и создания тега. Валидность ключа и доступность сетевых зависимостей
проверяются при самой сборке.

`--version` — общая версия `MAJOR.MINOR.PATCH`: она попадает в .NET-бинарники,
MSI ProductVersion, Android versionName и имена файлов. Ограничения MSI:
major/minor до 255, patch до 65535. Выбирайте версию выше уже установленной.

`--android-version-code` — отдельное целое число, обязательно **больше всех
ранее выпущенных versionCode**. Оно не выводится из номера версии автоматически,
чтобы можно было выпускать повторные Android-сборки. APK проверяются через
`apksigner verify`; идентификатор пакета и обе версии — через `aapt`.

## Результат

После успешного завершения в `artifacts/<version>/` находятся ровно девять файлов:

```text
prism-host-<version>-win-x64.msi
prism-host-<version>-win-x64.zip
prism-library-<version>-win-x64.msi
prism-library-<version>-win-x64.zip
prism-host-<version>-linux-x64.tar.gz
prism-library-<version>-linux-x64.tar.gz
prism-player-<version>-android.apk
prism-library-<version>-android.apk
SHA256SUMS.txt
```

Готовый каталог появляется только после сборки всех восьми пакетов и расчёта
SHA-256. Существующий релиз скрипт не перезаписывает. При ошибке возвращается
ненулевой код завершения. Промежуточные файлы сохраняются в отдельном
`artifacts/build-*` для диагностики; их можно удалить после проверки.
Скрипт использует обычные каталоги сборки проектов: не запускайте одновременно
два релиза или другую сборку тех же проектов.

После создания пакетов скрипт повторно проверяет чистоту рабочего дерева и
неизменность HEAD, затем создаёт лёгкий тег `v<version>` на коммите, зафиксированном
перед сборкой. Существующий тег не перезаписывается; `git push` не выполняется.
При ошибке сборки тег не создаётся. Если ошибка произошла только на этапе
создания тега, готовые пакеты сохраняются, а скрипт сообщает об ошибке: нужно
проверить соответствие исходного коммита и поставить тег вручную. Не меняйте
исходники и не переключайте коммиты во время сборки.

В ZIP лежат консольные приложения с `start.cmd`, в TAR.GZ — с `start.sh` и
примерами systemd-служб. Linux-бинарникам и скриптам выставляется исполняемый бит
внутри архива даже при сборке на Windows. Инструкции находятся внутри архивов.
Windows-лаунчер включён в оба Windows-пакета хоста; Linux-лаунчера нет.
Веб-клиент собирается один раз и включается во все пакеты сервера библиотеки.
Приложения публикуются без .NET runtime. Используются начальные настройки,
локальные данные, логи и ключи подписи не упаковываются.

## Зависимости на целевом компьютере

- Хост и сервер библиотеки: ASP.NET Core Runtime 10 x64.
- Windows-лаунчер: дополнительно .NET Desktop Runtime 10 x64.
- Ubuntu x64: системные зависимости .NET 10 для выбранной поддерживаемой версии
  Ubuntu. Архив не является DEB-пакетом и не устанавливает их автоматически.

MSI использует `WixToolset.Netfx.wixext` / `DotNetCompatibilityCheck` и стандартный
`Launch`: проверяет совместимую среду 10.0.x x64, сообщает о недостающей
зависимости до установки. .NET не скачивается и не встраивается. Проверки
не блокируют обслуживание/удаление уже установленного продукта (`Installed`).
Собственных проверяющих программ или PowerShell-действий в MSI нет.

FFmpeg/FFprobe входят в пакеты хоста. URL и SHA-256 закреплены в `ffmpeg.json`;
кэш находится в `artifacts/cache`. При изменении версии FFmpeg нужно обновить
адрес и контрольную сумму. Windows использует ту же сборку Gyan, что существующий
MSI, Linux — сборку BtbN с ветки 8.1, сохранённую на конец месяца. Поставщики
могут удалять старые архивы: сохраняйте проверенный кэш для повторных сборок.
В архивы включаются лицензии и сведения о поставщике из исходных пакетов FFmpeg.

Результат воспроизводим по составу и версиям; побайтовая идентичность не
гарантируется из-за временных меток и метаданных сборочных инструментов.

## Проверка самого скрипта

```powershell
python -m unittest discover -s scripts/tests -v
```

Полный запуск проверяет реальную компиляцию, штатную валидацию WiX, подписи APK
и их версии. Он не заменяет проверку установки MSI на чистой Windows и запуск
Linux-пакетов на целевой Ubuntu.
