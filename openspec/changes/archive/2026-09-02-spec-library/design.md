## Context

Baseline-документирование уже реализованного и работающего поведения
`Prism.Library` (см. proposal.md — Why и `TODO.md`, п.14). Код не меняется;
«реализация» — файлы спецификаций в `openspec/specs/library/...`.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение библиотеки шестью спеками: агрегация
  каталога хостов, дерево и мета, правила автозаполнения, ремап отпечатков,
  плееры, раздача веб-клиента.

**Non-Goals:**
- Не меняется и не улучшается поведение библиотеки.
- Не специфицируются внутренние компоненты (`HostCatalog`, `FileHostLedger`,
  `LibraryMaintenanceService`, EF-модели) — спеки описывают контракт API и
  наблюдаемые эффекты, а не реализацию.
- `Prism.Client` не специфицируется отдельными требованиями «что показывает
  экран»: он раздаётся библиотекой и целиком строится поверх её API, поэтому
  здесь фиксируется только контракт раздачи статики и правило same-origin
  (`web-client-hosting`), а не разметка или взаимодействия интерфейса.
- Контракты хоста (`/api/media`, `/api/resolve`, `/api/media/{id}/successor`)
  не переспецифицируются — они принадлежат `spec-host`; здесь описано только
  то, как библиотека их использует (агрегация, ремап).
- Протокол MQTT-сообщений плееров (`Prism.Mqtt`, топики `info`/`state`/`cmd`,
  формат payload) не расписывается протокольно — библиотека и лаунчер делят
  этот код, а спека здесь описывает только наблюдаемое поведение HTTP API
  библиотеки поверх него (`library/players`).

## Decisions

- **Шесть капабилити по осям изменения.** `catalog-aggregation` (что видно
  клиенту из объединения хостов), `tree-and-metadata` (собственная структура
  библиотеки), `auto-rules` (декларативная раскладка новых файлов),
  `fingerprint-remap` (переживание переездов/докачек и обслуживание),
  `players` (интеграция с MQTT-плеерами), `web-client-hosting` (раздача
  статики) — каждая меняется по своей причине: новый хост в конфиге не
  затрагивает правила, новое правило автозаполнения не затрагивает плееры и
  т.д. Альтернатива (одна капабилити «library») отклонена по тем же
  соображениям, что и в `spec-host` (см. его design.md).
- **`fingerprint-remap` выделена отдельно от `catalog-aggregation`**, хотя обе
  используют бухгалтерию «id → хост»: агрегация каталога — про то, что видит
  клиент прямо сейчас; ремап и GC — про то, как библиотека переживает изменения
  на хостах во времени. Это разные жизненные циклы требований.
- **`players` не включает протокол MQTT** — топики и формат сообщений
  специфицированы через наблюдаемое поведение HTTP API (`/api/players`,
  `/api/players/{id}/open`), а не как отдельный протокольный контракт: сам
  протокол (`Prism.Mqtt`) общий с лаунчером и не принадлежит только библиотеке.

## Risks / Trade-offs

- [Спеки могут разойтись с кодом при будущих изменениях библиотеки] →
  следующие change обязаны обновлять затронутые требования дельтами.
- [Формулировки — интерпретация кода `LibraryEndpoints`/`HostCatalog`/
  `LibraryMaintenanceService`/`PlayerEndpoints`, возможны мелкие неточности] →
  сверка по коду вынесена отдельными пунктами в tasks.md.
- [Границы с `spec-host` и общим `Prism.Mqtt` неочевидны при будущих
  изменениях, требования могут задваиваться] → design.md фиксирует эти
  границы явно (см. Non-Goals), последующим change стоит на них ссылаться.
