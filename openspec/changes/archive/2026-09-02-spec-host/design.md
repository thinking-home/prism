## Context

Это baseline-документирование уже реализованного и работающего поведения
`Prism.Host` (см. proposal.md — Why). Код не меняется; единственная
«реализация» — файлы спецификаций в `openspec/specs/host/...`. Технических
решений в обычном смысле (архитектура, зависимости, миграция данных) здесь нет —
раздел ниже фиксирует только то, как границы поведения хоста разложены по
спекам, чтобы не разъезжались при будущих изменениях.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение HTTP API хоста тремя спеками:
  каталог/сведения о сервере, доставка видео, контентная идентификация.
- Дать основу, на которую будут ссылаться будущие change для `Prism.Host`.

**Non-Goals:**
- Не меняется и не улучшается поведение хоста.
- Не специфицируются внутренние классы (`HlsTranscoder`, `TranscodeSession`,
  `MediaResolveService` и т.п.) — спеки описывают контракт, не реализацию.
- Не специфицируется `Prism.Host.Console`/`Prism.Host.Service`/`Prism.Host.Setup`
  как отдельные слои — это обвязки запуска одного и того же приложения, у них
  нет собственного наблюдаемого поведения API.

## Decisions

- **Три капабилити вместо одной.** `media-catalog` (что хост знает о файлах),
  `streaming` (как он их отдаёт) и `content-identity` (как он их узнаёт) — это
  разные оси изменения: правила автозаполнения библиотеки будущего меняют
  первую, добавление нового кодека — вторую, а логика ремапа — третью.
  Альтернатива (одна большая спека `host`) отклонена: будущие изменения чаще
  затрагивают одну ось, и общая спека росла бы неконтролируемо.
- **`content-identity` выделена отдельно от `media-catalog`**, хотя id — поле
  записи каталога: резолв и поиск преемника (`/api/resolve`,
  `/api/media/{id}/successor`) существуют ради внешних потребителей (лаунчер,
  библиотека) и меняются по их логике ремапа, а не по логике каталога.
- **Дорожки из соседних файлов отнесены к `streaming`, а не к `media-catalog`**:
  они описывают, откуда берётся дорожка для доставки (companion-файл), а не
  структуру каталога как такового; список дорожек в карточке — следствие этого
  правила.
- **`Prism.Client` не специфицируется в этом изменении** — веб-клиент раздаётся
  библиотекой и работает через агрегированный каталог `Prism.Library`, поэтому
  его поведение относится к `spec-library` (см. proposal.md — Impact).

## Risks / Trade-offs

- [Спеки могут разойтись с кодом при будущих изменениях хоста, если правки
  вносятся в обход OpenSpec] → последующие change для хоста обязаны обновлять
  затронутые требования дельтами, а не менять поведение мимо спек.
- [Формулировки в спеках — интерпретация существующего кода, а не выгрузка из
  него; возможны мелкие неточности] → пункт «Проверить» у планировщика просит
  сверить составленные спеки с фактическим поведением перед архивацией.
