# library/fingerprint-remap Specification

## Purpose
Идентификатор файла — контентный, поэтому переезд, докачка или замена
содержимого по тому же пути меняют id; библиотека переносит записи (мету,
членство) на новое содержимое автоматически и умеет находить, у какого хоста
спросить о судьбе конкретного файла, не опрашивая все хосты подряд.

## Requirements

### Requirement: Обнаружение осиротевших записей
Фоновое обслуживание SHALL на каждом проходе определять записи (членство или
мету файлов), чей id больше не встречается ни у одного доступного хоста
(«осиротевшие»), и пытаться найти для них преемника.

#### Scenario: Файл пропал из живого списка
- **WHEN** id файла, у которого есть записи в библиотеке, больше не встречается в списке живых файлов
- **THEN** ближайший проход обслуживания пытается найти для него преемника

### Requirement: Перенос записей на преемника
Если для осиротевшего id найден преемник (новый id по тому же последнему
известному пути) и у преемника ещё нет собственных записей — библиотека SHALL
перенести на него всю мету и членство осиротевшего id. Если у преемника уже
есть собственные записи (конфликт) — перенос SHALL не выполняться, записи
осиротевшего id SHALL остаться как есть.

#### Scenario: Преемник свободен
- **WHEN** осиротевший id имеет преемника без собственных записей в библиотеке
- **THEN** мета и членство переезжают на id преемника, записи осиротевшего id больше не существуют

#### Scenario: Преемник уже занят
- **WHEN** у найденного преемника уже есть собственные записи меты или членства
- **THEN** перенос не выполняется, записи осиротевшего id не трогаются

### Requirement: Ремап выполняется раньше автозаполнения
В рамках одного прохода обслуживания перенос осиротевших записей SHALL
выполняться раньше применения правил автозаполнения, чтобы файл-преемник,
получивший перенесённые записи, не был ошибочно принят правилами за
нетронутый.

#### Scenario: Преемник получает перенесённые записи раньше правил
- **WHEN** в одном проходе обслуживания есть и ремап осиротевшего файла, и файлы, подходящие под правила автозаполнения
- **THEN** файл-преемник считается тронутым (имеет перенесённые записи) и правила его не переразмечают

### Requirement: Адресный поиск преемника через бухгалтерию «id → хост»
Библиотека SHALL запрашивать преемника только у хостов, ранее видевших
соответствующий id (по внутренней бухгалтерии, пополняемой при каждом опросе
каталога), не опрашивая остальные сконфигурированные хосты ради одного файла.
Id, отсутствующий в бухгалтерии, SHALL считаться без преемника.

#### Scenario: Преемник ищется только у видевших файл хостов
- **WHEN** запускается поиск преемника для id, который бухгалтерия связывает с одним конкретным хостом
- **THEN** запрос преемника уходит только к этому хосту, остальные хосты не опрашиваются

### Requirement: Сборка мусора по явному запросу
`POST /api/library/gc` SHALL удалять записи (членство, мету, бухгалтерию
«id → хост»), чей id не встречается среди живых файлов ни одного хоста, и
возвращать число удалённых записей каждого вида. Автоматическая очистка SHALL
не выполняться — только по явному запросу.

#### Scenario: Запрошена сборка мусора
- **WHEN** отправлен `POST /api/library/gc`, и в библиотеке есть записи файлов, отсутствующих на всех хостах
- **THEN** эти записи удаляются, ответ содержит число удалённых членств, мета-записей и строк бухгалтерии

#### Scenario: Сборка мусора не запускается автоматически
- **WHEN** проходит плановое фоновое обслуживание без явного запроса `gc`
- **THEN** записи отсутствующих файлов не удаляются
